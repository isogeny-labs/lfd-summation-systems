# Quadratic-subfield S3 scaling panel

## Scope and fixture provenance

This is a same-target, cold-cost screen of the direct binary S3 quadratic
subfield oracle on three *selected* curves. The n16 fixture comes from the
earlier direct-oracle screen. The n20 and n24 fixtures were selected during
exploratory curve-order searches before this panel was frozen. They are not a
random sample of binary curves, and the measured result does not transfer to
prime-degree fields or generic prime-field ECDLP.

Run `sage -python experiments/subfield-s3-scaling-20261127/verify.py` to
regenerate all nine targets and compare every deterministic field of the
committed `results.json`. Wall and CPU times are recorded, but are omitted
from exact replay comparison because host scheduling changes them. The
script checks every emitted relation by point addition and S3, checks the
subgroup order and factor-base coset, and checks each recovered scalar by
public-point multiplication.

Sage 10.10.rc0 on macOS 27.2 arm64; PR source and `results.json` are the
measurement record. All target scalars are generated by
`Random(20261127 + r)` and used only to check answers; the solvers receive
the same public generator and target. The online walk uses seed
`20261127 + i` for target index `i` and eight seeded increment points.
The same seed initializes rho. There are three targets for each curve.

Here `E: y²+xy=x³+a2*x²+b6` over `GF(2^n)`, with the factor-base
abscissas in `GF(2^k)`. Each curve has order `2r`, with prime `r`, and its
`j=1/b6` lies outside the proper subfield. The code enumerates all subfield
abscissas to check that every nonzero base point has the even-coset property.
This fixture check and generator selection are outside all three algorithm
timers; they are common validation rather than claimed free runtime setup.

## Mathematical relation and cost boundary

For a nonzero subgroup point `Q` with `t=x(Q)` outside the subfield, write
`s=x1+x2` and `p=x1*x2` for subfield abscissas. Binary S3 is
`p²+t²s²+tp+b6=0`. Conjugation by `2^k` gives
`p=A*s²+C`, where `A=t+t^(2^k)` and `C=(b6+b6^(2^k))/A` lie in the
subfield. With `u=s²`, substitution gives the subfield quadratic
`A²*u²+N*u+D=0`, where `N=t*t^(2^k)` and `D=C²+t*C+b6`.
Solving this quadratic, then `X²+sX+p`, yields candidate pairs. Each pair
is lifted and checked against actual point addition. Thus the local
subfield oracle has quadratic equations; this says nothing by itself about
the degree or cost of the complete target solver.

For a signed relation `s1*P1+s2*P2=Q=aG+bT`, the coset condition makes
`2Pj=hjG`. Hence each accepted row is
`s1*h1+s2*h2-2b*d=2a (mod r)`, where `T=dG`.
Sparse online elimination handles base-log columns and the target column;
it stops only when a row determines and verifies `d`.

The online timer includes its Artin–Schreier table, eight increment points,
starting point, one group addition per query, all failed queries, lazy point
lifts, exact oracle work, elimination, and final answer check. BSGS includes
its cold baby table and giant walk. Rho includes seeded initialization,
three-way walks and any restart. Curve construction, point counting, base
enumeration and generator selection are outside all timers. All methods run
in the same Sage process on identical `G,T`; no reusable online setup is
amortized across targets.

All three methods recovered and verified all nine seeded scalars. For these
fixtures and this implementation, the online quadratic-S3 method was slower
than both cold BSGS and the implemented rho walk on every target. The
favorable relation-count scaling did not pay for field arithmetic, lifting,
or elimination. The n24 third run had a larger wall/CPU gap, so its CPU
record is especially useful for comparison. Rho is a deterministic
three-way Floyd implementation, not a highly optimized native solver;
BSGS is also Sage code. Any crossover claim needs larger matched panels,
stronger generic baselines, and a full cost model.

This is a negative cost screen of the direct quadratic subfield route at
these sizes, not a theorem that every subfield construction loses. The
mathematical validity of individual relations is separately checked in the
code. Candidate selection and three seeds per size limit statistical claims.
