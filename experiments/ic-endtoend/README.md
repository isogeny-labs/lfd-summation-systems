# End-to-end PKM prime-field index calculus against Pollard rho, fully charged

**Every number on this page is `[pcc:unverified]`**: measured on one
4-core cloud container on 2026-11-20, no pcc claim filed, no replay
certificate, no validator report. It is not a leaderboard or benchmark row.

Preregistration: [`PREREGISTRATION.md`](PREREGISTRATION.md), committed alone
before any data (commit `aa362f6`). Code: Rust crate in this directory (`src/`).
Raw rows: `results/{yield,e2e,rho}.jsonl`; run logs `results/*.log`; every
table generated by `ic-endtoend report` in [`results/summary.md`](results/summary.md);
figures `results/fig-yield.svg`, `results/fig-cost.svg`.

## Question

The paper bounds the cost of one relation-search attempt by a Macaulay-matrix
solver. To compare the whole attack with Pollard rho one also needs the
**relation yield** and the **linear-algebra stage**. This experiment measures
both exactly, runs the attack end to end on prime-order curves with
`N` from `2^20` to `2^40`, verifies every logarithm, and runs rho on the same
curves and targets. Growth of the solving degree for `m >= 3` is handled
elsewhere.

## Method

* **Setting (PKM Section 3.3).** `p = c*2^K + 1` (smallest prime `>= 2^b`,
  `K = min(b-4, 24)`), `E: y^2 = x^3 + ax + b` of prime order `N` (orders by
  baby-step giant-step and a primality proof via the Hasse interval; the
  `b = 16` orders were checked against a naive point count). Factor base
  `F = {P : x(P) in t*H_k}`, `H_k` the subgroup of order `2^k` of `F_p^*`,
  `t = 1` (subgroup) or a coset. `f = |F|/2` classes, `|F|` measured.
* **Yield (exact, never Groebner).** `m = 2`: an exact census of the sum set
  `{P_i +- P_j}` (distinct x-coordinates, `Pr = 2|S_x|/(N-1)` exactly) when
  `2f^2 <= 2^26`, and in every cell sampling with `x(R - Q) in t*H_k` over all
  `Q in F` (hash lookups, batched inversion). `m = 3`: sampling with meet in
  the middle (`x(R - Q)` against the table of all `x(P_i +- P_j)`).
  Model tested: `Pr = 1 - exp(-lambda)`, `lambda = |F|^m/(m! N)`.
  Controls: random factor base of the same size (negative), arithmetic
  progression `{+-jG}` (positive), two curves per prime (A/A).
* **End to end.** Random walk `R <- R + S_t` (32 steps `S_t = c_t G + d_t Q`,
  index drawn independently of `R` so the walk cannot cycle), one group
  addition per attempt. `m = 2`: table of all `x(P_i +- P_j)` (built once, about
  `f^2` additions) and one lookup per attempt. `m = 3`: same table and, per
  attempt, `|F| = 2f` additions and lookups (meet in the middle). Relations are
  collected until a dependency is certain (`m = 2`: exact signed union-find,
  a balanced cycle or two unbalanced cycles; `m = 3`: 2-core rows exceed 2-core
  columns, checked every `max(8, f/128)` relations from `0.75 f`), the matrix is
  peeled to its 2-core and scalar Wiedemann (Berlekamp-Massey) gives one
  left-kernel vector `lambda`; `log Q = -sum lambda_j a_j / sum lambda_j b_j`,
  verified by `x*G == Q` (3 targets per cell, all 99 runs verified).
* **Rho.** r-adding walk, `r = 32`, distinguished points (`2^-8`), new walk
  per distinguished point (start = previous start + D, one addition),
  coefficients recovered by replaying the two colliding walks (charged). With
  the negation map (canonical representative, look-ahead against 2-cycles,
  fruitless-cycle detection and doubling escape) and without. 400 trials per
  variant and size; the e2e targets are the first three. All 4800 solved.
* **Charging.** Group additions (doublings, setup scalar multiplications,
  table, walk, search, resolution, replays) are 1 GAE each. Every other counted
  operation (hash lookups and inserts, multiply-adds mod `N` in the linear
  algebra, walk-index and distinguished-point tests, union-find and peeling
  steps) is priced at 0, 0.1 and 1 GAE; arms are ranked only where the order
  holds at all three prices. Field multiplications are inside the group
  additions and not charged twice. Primary rho baseline: with negation map.

### Relations needed and the linear-algebra stage `[pcc:unverified]`

| m | runs | median r*/f | range | median LA multiply-adds / (m n_core^2) |
|---|---|---|---|---|
| 2 | 51 | 0.532 | 0.045 - 0.944 | 6.18 |
| 3 | 48 | 0.922 | 0.779 - 1.194 | 4.73 |

`r*` = relations collected when the dependency was found, `f` = classes.
For `m = 2` the relation matrix is a signed graph and one dependency (a
balanced cycle) suffices for one logarithm, so about `f/2` relations are
needed, not `f + slack`, and the 2-core has only 2 to 58 columns: the linear
algebra is negligible (at most `4e4` multiply-adds against `>= 1e4` group
additions in every `m = 2` cell). For `m = 3` the threshold is the 3-XORSAT
2-core threshold `0.918 f`; the `m = 3` linear algebra is `~4.7 * 3 n_core^2`
with `n_core ~ 0.65 f`, i.e. about `6 f^2` multiply-adds, below the
generic model `m |F|^2 = 12 f^2`. One `m = 3` cell (`log2 p = 24`, `k = 10`,
`lambda = 8.6`) needed only `0.80 f` because the search takes the first
decomposition found, biasing rows toward low-index columns.

### Groebner route for `m = 2` (recorded, not run) `[pcc:unverified]`

Per attempt, the degree-`D` Macaulay matrix in `2k` chain variables has
`sum_{d<=D} C(2k, d)` columns. With the measured attempt counts, at the
certified LFD (`D = 5` for `k = 6..9`, `6` for `k = 10..13`), the column count
times attempts is `1.1e7` (`log2 p = 20`, `k = 5`) to `2.4e13`
(`log2 p = 40`, `k = 12`), against rho's `7e3` to `9e5` group additions; at the
ceiling `D = k + 2` the per-attempt columns are `1e3` to `6e7`. The paper's
per-failure bound `C(2k, floor((k-10)/14)+1)` is `1` for `k <= 9` and `2k`
for `10 <= k <= 23`, so at these depths it adds at most a factor `2k` to the
attempts, which the enumeration already beats (one addition and one lookup per
attempt). Swapping the enumeration for a Groebner solver can only raise the
`m = 2` cost above the rows shown. Full table in `results/summary.md`.

## Why `m = 2` cannot beat rho (and what the measurements add)

The expectation stated with the task, "factor base `>= sqrt N` forces LA
`>= N`", is not the binding mechanism in these runs: at the cost optimum
`f ~ (N/16)^(1/3)` and the `m = 2` linear algebra is a cycle search costing
almost nothing. The binding cost is the **relation search**. With the yield
model confirmed, `m = 2` needs about `f/2` relations at probability
`(2f)^2/(2N)` each, i.e. `~N/(4f)` attempts, and the cheapest exact test needs
either `2f` operations per attempt (enumeration: total `~N/2`) or a `~f^2`
pair table (total `~f^2 + N/(4f) >= ~N^(2/3)`). Either way the cost is
`>= N^(2/3)`, against rho's `sqrt(pi N/4)`. The measured exponent `0.69` matches
`2/3`. Any per-attempt solver that costs more than one lookup (the Groebner
route) only raises it. For `m = 3` with meet in the middle the same
`N^(2/3)` scaling holds with a larger constant (measured slope `0.78` over a
cap-limited `k` range).

## What larger sizes would need (no spend)

Time on this 4-core container: yield sweep 13.6 min, end to end 3.5 min
(`2^40`, `m = 2`: 35 to 75 s per target), rho 1.9 min.

* `m = 2` at `N ~ 2^48`: optimum `f ~ 2^14.7`, pair table `~2^29` entries
  (`~16 GB` at 16 bytes per slot and half load); capping memory at 8 GB
  (`f = 2^14`) gives `~2^32` attempts, about 40 min per target on 4 cores.
  At `2^56`: table `2^34` entries (`~0.5 TB`) or `2^40` attempts per target.
* `m = 3` (meet in the middle) at `2^48` with `f = 2^12`:
  `~1.4 N/f = 2^36.5` element tests, about 20 to 40 min per target.
* Rho at `2^48`: `2^23.8` additions per trial, 400 trials in about 20 min.
* Beyond memory, nothing in the measurements suggests the ordering changes:
  the gap grows like `N^(0.2)`.

except for thread scheduling, which does not change results.

## Deviations from the preregistration

* Cells were selected with the nominal `|F| = 2^k` in `lambda` (the
  measured `|F|` differs by a few percent); this changes which cells exist,
  not how they are scored.
* `m = 2` end-to-end `k` values were capped by the `2^25`-entry table at
  `log2 p = 40` (`k = 14` excluded), as preregistered; the optimum sits at the
  cap there, which steepens the measured `m = 2` slope slightly.
* The Groebner-route ceiling for `m = 3` (`3k + 1`) is recorded in
  `results/e2e.jsonl` only, not tabulated.
* No PDF was produced (no SVG-to-PDF converter in the container); the SVG
  figures are the visual record.

## Limits

Small sizes only (`N < 2^41`); one curve per size for the end-to-end and rho
runs (two for the yield); three targets per end-to-end cell, so per-cell
relation counts are noisy (`m = 2` `r*/f` ranges from `0.05` to `0.94`); the
Groebner route is costed from column counts, not run; `m >= 4` and the
solving-degree growth for `m >= 3` are out of scope. Not validated under the
validation gate; not a leaderboard row.
